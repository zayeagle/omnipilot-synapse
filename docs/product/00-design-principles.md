# OmniPilot Synapse · 产品设计理念与判据

> **立场**：笔记软件的竞争力不在功能多少，而在两件事——**它是否真正懂用户怎么思考、怎么积累知识**，
> 以及**AI 介入的方式是否让人舒服、不添乱**。本文件把这句话变成可判定的判据与门禁：任何 Feature 的设计与评审都必须过这里。

---

## 一、对用户知识工作流的理解深度

**知识工作流**是一个人从接触信息到把信息变成自己的知识、再输出应用的完整过程：

```
捕获 → 暂存 → 整理 → 连接 → 提炼 → 复习 → 输出 → 应用
```

**理解深度 = 是否清楚用户在每个环节的真实行为、心理与痛点**，而不是想当然地设计功能。

| 阶段 | 用户的真实处境 | 产品承诺 | 我们的取舍（克制点） |
|------|----------------|----------|----------------------|
| **捕获** | 地铁上、走路、聊天中看到好文章；不想分类，只想"先扔进去别丢" | **零压力**：一键入库，不强迫分类、不弹表单 | 不做"保存前选目录"这类看似专业、实则收取心流税的功能 |
| **暂存** | 收件箱是缓冲区不是垃圾场；需要"还有多少待处理"的确定感 | 待处理数量可见、可进入、可清空 | 不做无限堆积的隐形队列：每条内容都要有出口 |
| **整理** | 晚上有空才愿意整理；希望 AI 先给建议，自己只做确认或微调 | **低负担**：AI 建议归属，人确认或微调 | 不让用户从零建文件夹；不自动改动用户的结构 |
| **连接** | "这条和之前那篇有关系"——关系常在整理时才浮现 | 提示相关笔记、建议挂载主题 | 不生成用户没确认的链接；不为展示"智能"而乱连 |
| **提炼** | 只有摘要没用；要能直接回填进自己的知识体系 | **结构化**：结论 / 适用场景 / 反例 / 相关节点 | 只提案不改写原文；AI 产出永远是候选 |
| **复习** | 等想不起来才打开软件就太晚了；遗忘临界点需要被提醒 | **主动出现**：到期提醒，自评后调整下次时间 | 不做强制弹窗；提醒可关、可推迟、可忽略 |
| **输出** | 真正要用时（写文章、做决策）找不到、引不出 | 一键取出可引用的素材（引用 / 大纲 / 片段） | 不做重型编辑器；只服务于"用得上" |
| **应用** | 知识只有被用过才算自己的 | 记录"用过 / 验证过"的回流痕迹 | 不发明复杂的工作流术语强加给用户 |

### 为什么这是壁垒

功能可以抄，**对用户行为细节的洞察与取舍很难抄**。flomo 故意不做复杂排版，是因为它深刻理解"速记时排版是负担"——
这种克制只能来自对工作流的深度理解。我们同样宁可少一个功能，也不要多一分心流税。

## 二、AI 与用户协作的优雅程度

**优雅 ≠ 全自动包办；优雅 = 人机像一对默契的搭档。**

| # | 特质 | 判定问题（能指着实现回答） | 反例 |
|---|------|---------------------------|------|
| E1 | **介入时机恰当** | 用户正在快速记录时，AI 是否保持安静；等用户停下才出现？ | 每次打开都强制等待生成摘要 |
| E2 | **建议而非命令** | AI 产出是否只是候选，用户能否一键忽略或修改，而结构不被擅自改动？ | 自动把笔记塞进某分类且改不了 |
| E3 | **可解释、可控制** | AI 能否说明"为什么这样建议"；用户能否撤销与调整？ | 只说"已为你整理"，看不出依据 |
| E4 | **学习用户偏好** | 用户多次拒绝的建议是否不再出现；常做的归属是否下次自动照做？ | 每次推荐同样的、已被拒绝的东西 |
| E5 | **错误可纠正** | AI 提炼错了，用户能否直接改，且修正被记住、下次更准？ | 只能删掉重来，改不了也学不会 |

**为什么优雅重要**：笔记软件是高频、私人的工具。协作不优雅，每次互动都在打断思考、增加决策负担，用户会关掉 AI 甚至换软件；
优雅则让用户觉得"它懂我"，从而长期依赖。

## 三、两轴合起来看：判据矩阵（可判定门禁）

工作流深度决定 **AI 在哪个环节、以什么方式帮忙**；协作优雅决定 **帮忙时用户是否舒服、是否愿意长期用**。
两者相乘，就是每个 Feature 必须通过的矩阵。

### 横切判据（W1–W6，最低门槛）

| # | 判据 | 判定问题 |
|---|------|----------|
| W1 | 捕获零心流成本 | 用户是否需要离开当前上下文、是否需要先做分类决策？ |
| W2 | 归宿可见 | 每条进入系统的内容，是否有一处必须由人处理的队列，且能看到它下一步去哪？ |
| W3 | 决策权在人 | AI 产出是否结构性只提案？是否有一处等人按下接受 / 改写 / 丢弃？ |
| W4 | 可逆与可理解 | 自动动作能否低成本撤回？冲突与失败是否可理解，而不是变成噪音？ |
| W5 | 检索即回报 | 模糊回忆（不记得原词）能否命中？ |
| W6 | 静默失败是可耻的 | 后台失败时，用户能否在 3 秒内知道哪里坏了、该做什么？ |

### 阶段判据（按 8 阶段逐条问）

进入是否零压力？处理是否低负担？离开是否有出口（不产生无出口状态）？失败是否可见？

### AI 介入验收（任一 AI 行为上线前必须全过）

E1 时机 · E2 建议性 · E3 可解释可控制 · E4 记忆偏好 · E5 可纠错。
**E4 与 E5 是当前产品最薄弱的两项**：任何涉及建议的功能，都必须同时给出"如何被拒绝"与"如何记住拒绝"。

## 四、参考旅程（自查用的验收剧本）

> 你读到一篇论文，随手分享进软件 → AI 提取标题作者，并建议"这篇可能属于『记忆机制』主题，要挂到知识树吗？"
> → 你点"确认" → 一周后，AI 根据复习记录提醒"『记忆机制』下三篇你上次自评『模糊』，今天要复习吗？"
> → 你点"复习"，AI 呈现核心结论，你自评"掌握"，它调整下次复习时间。
> 全程你只点了三四次：没有填表、没有手动分类、没有被强制弹窗。

任何一个 Feature，都要能在这条旅程里指出自己的位置，并证明它**没有**给用户增加额外的点击、表单或等待。

## 五、每个 Feature 的必答四问（写进 `04-design.md`）

1. **工作流位置**：用户此刻在第几阶段？这一步是因为用户需要，还是因为我们的数据模型需要？
2. **决策权**：这一步谁做决定（人还是 AI）？AI 只提案吗？人有没有一个必须按下的决定点？
3. **产物与可逆性**：决定之后产物去哪？能否低成本撤回？是否留下"无出口状态"？
4. **失败可见性**：这一步失败时，用户 3 秒内知道原因与该做什么吗？

涉及 AI 的功能，另需逐条自查 E1–E5。

## 六、CR 门禁清单（逐条勾选）

- [ ] 新功能没有增加捕获阶段的心流成本（无强制表单 / 分类 / 等待）
- [ ] 每条新产生的数据都有"人能看到并处理"的出口（不制造新的无出口状态）
- [ ] AI 只产出候选；接受 / 改写 / 丢弃三选一齐全，且原始内容不被改写
- [ ] 自动动作可撤回；不可撤回的动作必须显式说明并默认不执行
- [ ] 后台失败有可读原因 + 一个可执行动作（不出现"未知错误"黑箱）
- [ ] 建议类功能记录了"拒绝"，并在下次抑制同类建议（E4）
- [ ] 纠正被记住（E5）：用户改过的内容下次被当作偏好，而不是被重新猜一遍
- [ ] 新文案双语齐备；新 request type 限扩展页面可发且受限流
- [ ] 不新增运行时依赖；不引入新的网络出网
- [ ] 既有测试基线不下降；新增行为有对应 TC

## 七、落地机制（防止文档写完即漂移）

- `AGENTS.md` 是非协商规则的入口，指向本文件；AI 与协作者开工前必须先读。
- `04-design.md` 每个 Feature 必须包含"工作流与协作"节（本文件 §5 的四问 + §2 的 E1–E5）。
- 本文件与审计文档受**契约测试**保护（`apps/extension/lib/tooling/design-docs.test.ts`）：结构缺失即测试失败——
  判据不会因为没人看而悄悄消失。
- 审计报告（`docs/audits/00-functional-audit.md`）按两轴逐条给出证据，并随每次需求更新。

## 八、已知反例库（我们自己的历史错误，持续追加）

| 反例 | 违反 | 教训 |
|------|------|------|
| AI 提炼出卡片后只写进 `cards/pending/`，产品内既看不到也没有接受 / 丢弃入口 | W2 / W3 / E2 / E5 | "AI 产出了"不等于"协作完成了"：没有决定点就没有协作 |
| 冲突保留为 `.conflict-<stamp>.md` 兄弟文件 | W4 / E3 | 保住数据是对的，但把理解成本丢给用户就是设计失职 |
| 同步失败只显示一个词，隐藏了原因 | W6 | 密钥卫生要保留，但不能用"什么都不说"换安全 |
| `Topic` / `ReviewState` 只有类型与存储格式，从未被创建 | W2 / 工作流深度 | 数据模型里有不等于工作流里有；"待实现"是最容易长期悬空的借口 |
| SSH 需要本地克隆，只在界面声明一句 | 工作流深度（配置阶段） | 物理约束不可消除，但可以把"要做什么"直接交到用户手上 |
